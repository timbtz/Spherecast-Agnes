## 1. What This Folder Is

`orchestration/` is the agent execution layer that sits between the enriched SQLite database and any external trigger (chat, schedule, webhook). It converts natural-language requests or system events into structured pipeline runs, executes DAGs of tools and LLM agents in dependency order, and returns logged, traceable results.

The folder ships in two sub-layers:

| Sub-layer | Path | Role |
|---|---|---|
| **API server** | `orchestration/api/` | FastAPI app: HTTP routes, DAG executor, run log, SSE streaming |
| **Agents** | `orchestration/agents/` | LLM reasoning nodes (Google ADK + Claude) |
| **Tools** | `orchestration/tools/` | Deterministic query/transform functions wired into pipelines |
| **Pipelines** | `orchestration/pipelines/` | YAML DAG definitions — one file per workflow |
| **Schema** | `orchestration/schema/` | `pipeline_schema.sql` — `orchestration.db` tables |

## 2. Architecture Summary

```
HTTP / chat trigger
       │
       ▼
orchestration/api/main.py          (FastAPI app, CORS, lifespan)
       │
       ├─ POST /chat                → router_agent.classify() → pipeline name + params
       ├─ POST /pipelines/run/{n}   → dag_executor.execute_pipeline()
       ├─ GET  /runs/{id}/stream    → SSE stream of node events
       └─ POST /data-update         → triggers proactive_consolidation
              │
              ▼
orchestration/api/dag_executor.py
  1. load_pipeline(name)           → reads YAML → Pipeline dataclass
  2. _topological_layers(nodes)    → Kahn's algorithm; produces parallel layers
  3. for each layer: asyncio.gather()
       ├─ node.tool_class   → get_tool(name)(ctx)          [synchronous, executor pool]
       └─ node.agent_class  → await get_agent(name)(ctx)   [async, ADK InMemoryRunner]
  4. ctx.node_outputs[node_id] = output
  5. write_event() to orchestration.db after every node
              │
              ▼
orchestration/api/agnes_context.py
  AgnesContext: run_id, pipeline_name, trigger_source, trigger_payload, node_outputs dict
  ctx.get(node_id) → prior node output dict
```

## 5. Pipeline YAML Schema

Pipelines live in `orchestration/pipelines/*.yaml`. Schema defined by `orchestration/api/pipeline_def.py`.

**Actual schema (as built):**
```yaml
name: supplier_fallout
trigger: chat          # chat | data_update | manual | schedule
nodes:
  - id: find-alternatives
    tool_class: SupplierAlternativesTool    # deterministic tool
    depends_on: []

  - id: gate-qualify
    tool_class: ComplianceGateTool
    depends_on: [find-alternatives]
    when: has_alternatives                  # named condition from conditions.py

  - id: write-proposal
    agent_class: ReactiveAgent              # LLM agent
    depends_on: [format-rfqs, bom-impact]
```

**Fields:**
- `name` — pipeline identifier; matches filename
- `trigger` — how the pipeline starts (informational only; executor doesn't enforce)
- `nodes[].id` — unique node key; also the `ctx.get(id)` lookup key
- `nodes[].tool_class` — registered in `agent_registry._TOOL_REGISTRY`
- `nodes[].agent_class` — registered in `agent_registry._AGENT_REGISTRY`
- `nodes[].depends_on` — list of node IDs that must complete first (DAG edges)
- `nodes[].when` — optional named condition; if falsy, node is skipped (output=None)

**Active pipelines:**

## 6. Persistence: `orchestration.db`

Separate from `db_enriched.sqlite`. Tracks pipeline run state and events.

```sql
-- pipeline_runs: one row per execute_pipeline() call
run_id TEXT PRIMARY KEY
pipeline_name, trigger_source, trigger_payload
status: pending | running | completed | failed
created_at, completed_at, error

-- pipeline_events: append-only event log per run
event_type: pipeline_started | node_completed | node_skipped | node_failed | pipeline_completed | pipeline_failed
node_id (nullable), data JSON, created_at
```

## 8. System Prompts — Markdown Files or Google ADK?

**Short answer:** System prompts are defined in Python as the `instruction=` parameter to `LlmAgent`. They can be either inline strings or loaded from markdown files — both work identically at runtime.

**Current state:** All system prompts are inline `_SYSTEM = """..."""` strings inside each agent Python file.

**Recommended approach** (from `REF-GOOGLE-ADK.md` and `REF-GOOGLE-ADK-RESEARCH-AGENT.md`): load from `.md` files:

```python
# orchestration/agents/reactive_agent.py
from pathlib import Path

_SYSTEM = (Path(__file__).parent / "prompts" / "reactive_agent.md").read_text()

agent = LlmAgent(
    name="reactive_agent",
    model="gemini-2.5-flash",
    instruction=_SYSTEM,
)
```

**Why markdown files are better for this project:**
- The `REF-GOOGLE-ADK-RESEARCH-AGENT.md` already contains the full ResearchAgent system prompt as a standalone markdown block — ready to be moved to a file
- Prompts are long (ResearchAgent's is ~100 lines) and mix prose, JSON, and numbered steps — hard to maintain inside a Python string
- Markdown files can be read and improved by future agent sessions without touching Python
- ADK has no native "load prompt from file" feature — it's just `instruction=Path(...).read_text()` — so this is a project-level convention, not an ADK constraint

**What NOT to do:** System prompts are not YAML pipeline definitions. YAML defines the DAG structure (node order, conditions, dependencies). System prompts define how an individual LLM node reasons — they belong in the agent Python file (or a companion `.md` file), not in the pipeline YAML.

**Recommended `prompts/` directory to create:**
```
orchestration/agents/prompts/
├── reactive_agent.md       ← reactive_agent.py _SYSTEM string
├── proactive_agent.md      ← proactive_agent.py _SYSTEM string
├── router_agent.md         ← router_agent.py _SYSTEM string
└── research_agent.md       ← full prompt from REF-GOOGLE-ADK-RESEARCH-AGENT.md §5
```
